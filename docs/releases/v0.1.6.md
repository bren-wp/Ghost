# Ghost FTP 0.1.6 Beta

Ghost FTP 0.1.6 Beta is a download-resume integrity and transfer-safety release for the native Windows/Linux FTP/FTPS client. It builds on the 0.1.5 parser, transfer-efficiency and workstation work without expanding the supported protocol or platform scope.

## Summary

This release changes partial-download resume from a size/offset-only optimization into a fail-closed identity-checked workflow. A `.ghostftp.part` file is resumable only when Ghost FTP can prove that it belongs to the same selected FTP endpoint and the same remote object revision using local bounded metadata plus server `SIZE` and `MDTM` information.

The supported protocol set remains FTP, Explicit FTPS and Implicit FTPS. Windows and Linux remain the only shipping targets. Ghost FTP remains free of application telemetry/tracking and shipping/regression projects retain zero third-party NuGet `PackageReference` dependencies.

## New

- Added bounded local resume metadata sidecars for partial downloads.
- Added endpoint/path/revision validation before issuing a REST-based resume.
- Added post-transfer remote identity verification to detect a remote file changing while bytes are in flight.
- Added an isolated, deterministic `GhostFTP.ResumeSelfTest` executable with no external server or package dependency.
- Added Windows and Linux CI gates specifically for safe download resume integrity.
- Applied the same resume-integrity path to files downloaded as part of recursive directory transfers.

## Safe download resume model

A partial file is stored as:

```text
<destination>.ghostftp.part
```

When the server exposes both `SIZE` and `MDTM`, Ghost FTP also stores a bounded local sidecar:

```text
<destination>.ghostftp.part.meta
```

The sidecar contains only the information needed to identify the transfer safely:

- metadata format version;
- selected FTP host;
- selected FTP port;
- selected FTP security mode;
- normalized remote path;
- remote file size;
- remote modification timestamp.

Passwords, usernames and transferred file contents are not written to the sidecar.

## Resume validation

Ghost FTP permits REST resume only when all of the following are true:

- the partial file exists and has a positive length;
- its length does not exceed the current server-reported file size;
- a valid bounded sidecar exists;
- host, port and security mode match the active connection;
- the remote path matches exactly;
- the current server `SIZE` matches the stored size;
- the current server `MDTM` value matches the stored remote revision timestamp.

If any check fails, the old partial/sidecar is removed and the download restarts from byte zero. Ghost FTP does not append unverified bytes merely because a `.ghostftp.part` file happens to exist.

## Compatibility with older partial files

Partial files created before 0.1.6 do not contain the new identity sidecar. They are intentionally treated as untrusted and are restarted from zero instead of being resumed blindly. This trades a one-time loss of an old partial download for stronger corruption protection.

## Remote mutation protection

After a transfer that began with a verifiable `SIZE` + `MDTM` identity, Ghost FTP queries those values again. If the remote object changed while the download was in progress, the locally completed result is discarded and the transfer reports an integrity error rather than presenting a potentially mixed-revision file as successful.

## Servers without reliable resume identity

If a server does not provide both usable `SIZE` and `MDTM`, Ghost FTP still performs a fresh download but does not retain an interrupted partial as safely resumable state. On failure/cancellation, an unverified partial is removed.

This is deliberate fail-closed behavior: resume is an optimization, while correct file identity takes priority.

## Recursive directory downloads

Directory-download planning and traversal limits remain unchanged, but each file in the plan now passes through the same identity-aware resume path. A stale partial belonging to one file cannot be accepted solely because its local filename and length look plausible.

## Security

- Resume metadata is local-only and capped at 16 KiB before deserialization.
- Metadata writes use a temporary local file followed by replacement/move semantics.
- Remote paths are normalized through the existing `InputGuard` boundary before they are used by the resume layer.
- A sidecar is tied to host, port and FTP security mode so a partial cannot be silently reused against another configured endpoint.
- Remote `SIZE`/`MDTM` data is parsed under existing bounded FTP control-reply limits.
- Existing FTPS certificate/hostname validation, no-downgrade behavior, `PBSZ 0`, `PROT P`, required `TYPE I`, strict EPSV/PASV parsing, listing bounds, traversal bounds and command-injection guards remain unchanged.

## Privacy

- Resume sidecars remain on the local device only.
- No credential, password or account token is stored in resume metadata.
- No telemetry, analytics, advertising, fingerprinting, cloud synchronization or background reporting was added.
- The deterministic resume test uses process-local loopback networking only.

## Stability and failure handling

- A corrupt, missing or oversized metadata sidecar causes a safe restart rather than a parser/transfer failure that leaves ambiguous state.
- A partial larger than the current remote object is discarded.
- If REST is unavailable, the existing transfer core falls back to a fresh download and stale resume state is not retained as trusted.
- A verified partial and matching sidecar can survive cancellation/transfer failure for a later retry.
- If a completed file fails the post-transfer remote revision check, the completed local result is deleted.
- Temporary metadata-write files are cleaned up best-effort.

## Testing

`GhostFTP.ResumeSelfTest` is a package-free deterministic loopback suite covering:

1. a valid partial resumes from the exact validated REST offset and produces byte-for-byte correct output;
2. a changed remote modification identity causes restart from zero with no stale byte mixture;
3. a same-size remote revision change during transfer is detected through the post-transfer MDTM check and the completed local file is discarded.

The suite is isolated from the broader protocol hardening executable so failures are attributable and the existing hardening lifecycle remains deterministic.

## Windows Setup and packaging

The installer architecture is unchanged. The maintained `GhostFTP-Setup.exe` remains the install/update/uninstall maintenance entry, with no separate `uninstall.exe`. Version metadata advances to `0.1.6`, file/assembly version `0.1.6.0` and informational version `0.1.6-beta`.

## Linux

The native Linux X11/XWayland renderer shares the same Core download/resume implementation as Windows. Resume identity rules are therefore cross-platform Core behavior rather than renderer-specific logic.

## Localization and UI

0.1.6 does not introduce a new user-facing screen or online localization dependency. The existing 29-language local catalog remains intact with English (`en`) as primary/default/fallback. Authentic UI capture remains a release gate even though this release is primarily Core/reliability work.

## Known limitations / upgrade notes

- Ghost FTP 0.1.6 remains Beta.
- SFTP/SSH is not implemented.
- Safe resume requires both usable `SIZE` and `MDTM`; otherwise interrupted downloads restart from zero.
- Servers whose `MDTM` precision cannot distinguish two replacements within the same reported timestamp granularity inherently provide a weaker remote identity signal; Ghost FTP does not claim cryptographic remote-content identity from FTP metadata.
- Existing pre-0.1.6 `.ghostftp.part` files are intentionally not resumed without the new sidecar.
- Queue pause still pauses dispatch only; it does not freeze an already-running FTP byte stream.
- Windows and Linux remain the only shipping application targets.
