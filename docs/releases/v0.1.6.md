# Ghost FTP 0.1.6 Beta

Ghost FTP 0.1.6 Beta is a download-resume integrity and transfer-safety release for the native Windows/Linux FTP/FTPS client. It builds on the 0.1.5 parser, transfer-efficiency and workstation work without expanding supported protocol or platform scope.

## Summary

This release changes partial-download resume from a size/offset-only optimization into a fail-closed identity-checked workflow. Downloaded bytes remain staged until the remote revision has been validated, so an existing local destination is not replaced by unverified data.

A `.ghostftp.part` file is resumable only when Ghost FTP can prove that it belongs to the same selected FTP endpoint and the same remote object revision using local bounded metadata plus server `SIZE` and `MDTM` information.

The supported protocol set remains FTP, Explicit FTPS and Implicit FTPS. Windows and Linux remain the only shipping targets. Ghost FTP remains free of application telemetry/tracking and shipping/regression projects retain zero third-party NuGet `PackageReference` dependencies.

## New

- Added bounded local resume metadata sidecars for partial downloads.
- Added endpoint/path/revision validation before issuing REST resume.
- Added staged destination commit: `.ghostftp.part` is not promoted over the destination until final validation succeeds.
- Added post-transfer remote identity verification to detect a remote file changing while bytes are in flight.
- Added fail-closed stale-partial cleanup: if untrusted bytes cannot be removed, transfer aborts before REST/RETR instead of falling back to length-only reuse.
- Added an isolated deterministic `GhostFTP.ResumeSelfTest` executable with no external server or package dependency.
- Added Windows and Linux CI **and Release** gates specifically for safe download resume integrity.
- Applied the same resume-integrity path to files downloaded inside recursive directory transfers.

## Safe download resume model

A partial file is stored as:

```text
<destination>.ghostftp.part
```

When the server exposes both `SIZE` and `MDTM`, Ghost FTP also stores a bounded local sidecar:

```text
<destination>.ghostftp.part.meta
```

The sidecar contains only transfer identity information:

- metadata format version;
- selected FTP host;
- selected FTP port;
- selected FTP security mode;
- normalized remote path;
- remote file size;
- remote modification timestamp.

Passwords, usernames, account tokens and transferred file contents are not stored in the sidecar.

## Resume validation

Ghost FTP permits REST resume only when all of these conditions are true:

- the partial exists and has positive length;
- its length does not exceed current remote size;
- a valid bounded sidecar exists;
- host, port and security mode match the active connection;
- remote path matches exactly;
- current server `SIZE` matches the stored size;
- current server `MDTM` matches the stored remote revision timestamp.

If the state is missing, malformed, oversized, legacy or stale, Ghost FTP removes it and starts from byte zero. If removal of untrusted staged bytes fails because of permissions, read-only state, filesystem failure or another local constraint, Ghost FTP aborts. It never continues into a legacy length-only resume path.

## Staged commit and destination preservation

0.1.6 treats `.ghostftp.part` as staged data until all applicable verification is complete.

For a normal verifiable download:

1. initial `SIZE` + `MDTM` establishes remote identity;
2. transfer/resume writes only to `.ghostftp.part`;
3. Ghost FTP queries `SIZE` + `MDTM` again;
4. only a matching revision permits `File.Move(..., overwrite: true)` onto the final destination.

This sequencing means an existing destination remains untouched when:

- the remote object changes while bytes are in flight;
- the post-transfer metadata query fails;
- stale partial cleanup fails;
- the transfer itself fails before verification.

A validated partial may remain available for a later safe resume when its trustworthy sidecar remains present.

## Full-length partial handling

A partial whose size already equals the remote `SIZE` is not automatically considered complete. Ghost FTP revalidates the current remote revision before promoting it to the destination. A changed revision invalidates the staged bytes rather than publishing them.

## Compatibility with older partial files

Partial files created before 0.1.6 do not contain the new identity sidecar. They are intentionally treated as untrusted and restarted from zero. This trades one-time reuse of legacy partial data for stronger corruption protection.

## Remote mutation protection

After a transfer that began with verifiable `SIZE` + `MDTM` identity, Ghost FTP queries those values again. If the remote object changed, staged bytes are discarded and the transfer reports an integrity error. A pre-existing destination is preserved.

FTP `SIZE`/`MDTM` is not a cryptographic content identity. Ghost FTP deliberately does not claim stronger identity guarantees than the selected server can provide.

## Servers without reliable resume identity

If a server does not provide both usable `SIZE` and `MDTM`, Ghost FTP can still perform a fresh download, but interrupted bytes are not retained as safely resumable state. On failure/cancellation, an unverified partial is removed.

Correctness takes priority over resume convenience.

## Recursive directory downloads

Directory traversal limits remain unchanged, but every file in the download plan uses the same identity-aware staged resume path. A stale partial belonging to another file/revision cannot be accepted merely because its filename or local length looks plausible.

## Security

- Resume metadata is local-only and capped at 16 KiB before deserialization.
- Metadata writes use temporary local files followed by replacement/move semantics.
- Endpoint, security mode and remote path are bound into resume identity.
- Server `SIZE`/`MDTM` replies remain under bounded FTP control-reply limits.
- Untrusted partial cleanup is required, not best-effort, before a fresh transfer may continue.
- Destination replacement is deferred until remote post-validation succeeds.
- Existing FTPS certificate/hostname validation, no-downgrade behavior, `PBSZ 0`, `PROT P`, required `TYPE I`, strict EPSV/PASV parsing, listing bounds, traversal bounds and command-injection guards remain unchanged.

## Privacy

- Resume sidecars remain on the local device only.
- No credential/password/account token is stored in resume metadata.
- No telemetry, analytics, advertising, fingerprinting, cloud synchronization or background reporting was added.
- Deterministic resume tests use process-local loopback networking only.

## Stability and failure handling

- Corrupt/missing/oversized sidecars never authorize resume.
- Partial files larger than the current remote object are rejected.
- REST refusal causes a proven restart from byte zero rather than silent stale-byte reuse.
- A verified partial with matching sidecar may survive cancellation/transfer failure for later retry.
- Remote-revision mismatch removes staged bytes while preserving an existing destination.
- Post-validation transport/control failure leaves the destination unchanged and retains only trustworthy staged state.
- Failure to delete untrusted staged bytes aborts safely before data transfer.

## Testing

`GhostFTP.ResumeSelfTest` is a package-free deterministic loopback suite. The complete 0.1.6 resume gate covers:

1. a valid partial resumes from the exact validated REST offset and produces byte-for-byte correct output;
2. changed remote identity restarts from byte zero without stale-byte mixture;
3. a same-size remote revision change during transfer is detected;
4. an existing destination survives that rejected in-flight remote mutation byte-for-byte;
5. failure to remove an untrusted stale partial aborts before REST and RETR.

The suite runs independently from the general protocol hardening executable so failures are attributable.

## Windows Setup and packaging

Installer architecture is unchanged. The maintained `GhostFTP-Setup.exe` remains the install/update/uninstall maintenance entry, with no separate `uninstall.exe`. Version metadata advances to `0.1.6`, file/assembly version `0.1.6.0` and informational version `0.1.6-beta`.

## Linux

The native Linux X11/XWayland renderer shares the same Core download/resume implementation as Windows. Resume identity and staged-commit rules are cross-platform Core behavior rather than renderer-specific approximations.

## Localization and UI

0.1.6 adds no online localization dependency. The existing 29-language local catalog remains intact with English (`en`) as primary/default/fallback. Integrity enforcement is independent of translated UI text.

## Known limitations / upgrade notes

- Ghost FTP 0.1.6 remains Beta.
- SFTP/SSH is not implemented.
- Safe resume requires both usable `SIZE` and `MDTM`; otherwise interrupted downloads restart from zero.
- FTP metadata may not distinguish two replacements within a server's reported timestamp granularity; this is not a cryptographic hash guarantee.
- Existing pre-0.1.6 `.ghostftp.part` files are intentionally not resumed without the new sidecar.
- Filesystem permission/lock problems that prevent stale-partial cleanup now fail closed and must be corrected before retry.
- Queue pause still pauses dispatch only; it does not freeze an already-running FTP byte stream.
- Windows and Linux remain the only shipping application targets.
